# ระบบค้นหาสินค้า — ที่เป็นอยู่ ทางเลือก และแผนต่อไป

เอกสารนี้ตอบสองคำถาม: **ตอนนี้เว็บเราค้นยังไง** และ **เว็บใหญ่ๆ (Shopee / Lazada / IKEA) เขาทำยังไง
แล้วเราควรเดินทางไหนต่อ**

---

## 1. สองระบบค้นหาที่มีอยู่ตอนนี้

ทุกอย่างวิ่งผ่าน `GET /materials/search` ตัวเดียว ต่างกันที่พารามิเตอร์ `mode`

| mode | ทำอะไร | เหมาะกับ |
|---|---|---|
| `keyword` | **จับคำให้ตรง** — พิมพ์ "โต๊ะ" ได้โต๊ะทุกตัว พิมพ์รหัสได้ตัวนั้น ไม่ตีความอะไรเพิ่ม | คำสั้น, รหัส MATNR/บาร์โค้ด, เซลล์ที่อยากได้ผลนิ่งๆ |
| `smart` | **ตีความประโยค** — "ตู้เสื้อผ้าสีแดง สูง 180 ไม่เกิน 5 พัน" → หมวด + สี + ขนาด + ช่วงราคา | ประโยคยาว มีสี/ขนาด/งบ |
| `auto` (ค่าเริ่มต้น) | จับคำก่อน ถ้าได้ศูนย์ค่อยไล่ผ่อน → เดาคำผิด → ตีความ → เข้าคำใดคำหนึ่ง | ลูกค้าทั่วไป |

ทำไม default ถึงเป็น "จับคำก่อน": โหมดตีความ **แคบกว่าเสมอ** เพราะมันเปลี่ยนคำเป็นตัวกรอง
คำว่า "โต๊ะ" ถ้าเอาไปกรองด้วยหมวดชื่อ "โต๊ะ" จะเหลือของแค่หยิบมือ ทั้งที่โต๊ะจริงๆ กระจายอยู่ในหมวดลูก
อีกสิบกว่าหมวด — เคสสั้นๆ แบบนี้จับคำให้ผลครบกว่าเสมอ

### โฟลว์เต็มของ `auto`

```
คำที่ลูกค้าพิมพ์
   │
   ├─ normalize      ตัวพิมพ์เล็ก · เลขไทย→อารบิก · ตัดเครื่องหมาย/wildcard
   ├─ แยกชนิดอักษร   "sofa3ที่นั่ง" → sofa | 3 | ที่นั่ง
   ├─ เป็นรหัสไหม     ตัวเลข ≥4 หลัก → เทียบ MATNR/SKU/บาร์โค้ด ทั้งแบบตัดศูนย์และเติมศูนย์ 18 หลัก
   ├─ ตัดคำไทย       "โซฟาหนัง" → โซฟา + หนัง   (longest-match กับคลังคำที่สร้างจากชื่อหมวด/สี/รุ่นในฐานเอง)
   ├─ ขยายคำพ้อง      sofa ↔ โซฟา · mattress ↔ ที่นอน · เกาอี้ ↔ เก้าอี้
   │
   ├─ (1) ค้นแบบเข้าครบทุกคำ ────────────► เจอ → จบ
   ├─ (2) เดาชื่อรุ่นที่พิมพ์ผิด แล้วค้นใหม่ ──► เจอ → ตอบพร้อม `corrected`
   ├─ (3) ตีความประโยคเป็นตัวกรอง ────────► เจอ → ตอบพร้อม `understood`
   │        └─ ถ้ายังไม่เจอ ผ่อนทีละอย่าง: ตัดขนาด → ตัดสี (บอกใน `dropped`)
   └─ (4) เข้าคำใดคำหนึ่งก็พอ ───────────► ตอบพร้อม `relaxed: true`
```

การจัดอันดับ (`sort=relevance`) เป็นคะแนนรวมหลายชั้น ไม่ใช่ if-else ชั้นเดียว:

| หลักฐาน | คะแนน |
|---|---|
| รหัสตรงเป๊ะ (MATNR / SKU / บาร์โค้ด) | 1000 |
| รหัสขึ้นต้นด้วย / มีรหัสนี้อยู่ข้างใน | 300 / 150 |
| ทั้งวลีอยู่ต้นชื่อ / อยู่ในชื่อ | 200 / 120 |
| รายคำอยู่ในชื่อไทย (ตรงตัว / ผ่านคำพ้อง) | 40 / 30 |
| รายคำอยู่ในชื่ออังกฤษ, ชื่อดิบ SAP, ซีรีส์, สเปก, สี | 18 |
| รายคำอยู่ในชื่อแบรนด์/หมวด | 10 |
| ขายดี (MAABC ชั้น Z) / มีรูป | 6 / 4 |

สองอันล่างตั้งใจให้น้อยๆ — เอาไว้ตัดสินเฉพาะตอนคะแนนเนื้อหาเสมอกัน ไม่ให้ของขายดีไปแซงของที่ตรงกว่า

### สิ่งที่ผู้ใช้เห็น

- **กล่องแนะนำใต้ช่องค้นหา** (`GET /materials/suggest`) — คำค้นยอดฮิตที่เคยเจอของ + หมวด + แบรนด์
  + สินค้า 6 ตัวที่ตรงที่สุดพร้อมรูปและราคา · เลื่อนด้วยลูกศร · เก็บคำค้นล่าสุดไว้ใน localStorage
- **บอกเสมอว่าระบบทำอะไรกับคำค้น** — `corrected` / `understood` / `relaxed` ขึ้นเป็นข้อความเหนือผลลัพธ์
  พร้อมลิงก์ "ค้นแบบตรงตัวแทน" · ผลที่ไม่ตรงเป๊ะแล้วไม่บอก คือที่มาของความรู้สึกว่า "เสิร์ชมั่ว"

## 2. เว็บใหญ่ๆ เขาใช้อะไรกัน

| แนวทาง | ใครใช้ | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **SQL `LIKE`** | เว็บเล็ก, ระบบหลังบ้าน | ไม่ต้องมีของใหม่ให้ดูแล ข้อมูลสดเสมอ | ไม่มีตัดคำ/ไม่ทนคำผิด/จัดอันดับไม่เป็น · ช้าเมื่อของเกินหลักแสน |
| **Postgres FTS + `pg_trgm`** | เว็บกลาง (ของเราขั้นถัดไป) | อยู่ในฐานเดิม ไม่มี service เพิ่ม · index จริง เร็ว · trigram ทนคำผิดได้ | ไม่มี analyzer ภาษาไทยในตัว (ต้องตัดคำเองแล้วเก็บลง `tsvector`) · จัดอันดับปรับได้จำกัด |
| **Meilisearch / Typesense** | เว็บกลาง–ใหญ่ที่อยากได้เร็ว | ตั้งค่าไม่กี่ชั่วโมง · typo tolerance + prefix + synonym + facet มาให้ในตัว · ตอบใน ~10ms · ตัดคำไทยได้ (Meili ใช้ charabia) | เป็น service เพิ่มที่ต้อง sync ข้อมูล · จัดอันดับซับซ้อนสู้ ES ไม่ได้ |
| **Elasticsearch / OpenSearch** | **Shopee, Lazada, Central, IKEA** | analyzer ไทย (ICU/thai) · ปรับสูตรจัดอันดับได้ละเอียด · รองรับ Learning-to-Rank, A/B test, personalization · สเกลได้ระดับพันล้านชิ้น | หนักที่สุด ต้องมีคนดูแลจริงจัง · แพง · overkill ถ้าของแค่หลักหมื่น |
| **Vector / semantic (embedding)** | ชั้นเสริมของทุกเจ้าข้างบน | เข้าใจความหมาย "โซฟานั่งสบายสำหรับห้องเล็ก" · ข้ามภาษาได้ | แพงและช้ากว่า · **ไม่แม่นกับรหัสสินค้าและคำเฉพาะ** · ตอบเป็นของใกล้เคียงตลอดแม้ควรตอบว่าไม่มี |

### ข้อสรุปที่สำคัญที่สุด

เว็บใหญ่ **ไม่ได้ใช้ AI แทนการค้นแบบจับคำ** — เขาใช้ซ้อนกันเป็นชั้นๆ:

```
คำค้น → [Query Understanding] → [Retrieval] → [Ranking] → [ผลลัพธ์]
         ตัดคำ/คำพ้อง/แก้คำผิด/    ดึงผู้สมัคร     จัดอันดับ
         ดึงสี-ขนาด-งบออกมา       ~1000 ตัว      ด้วยความตรง+ยอดขาย+CTR
                                  (lexical +
                                   vector)
```

ชั้นที่ให้ผลคุ้มที่สุดต่อแรงที่ลง คือ **Query Understanding** (ชั้นซ้ายสุด) ไม่ใช่ vector —
และนั่นคือชั้นที่เราเพิ่งทำไปในโค้ดชุดนี้ (`app/services/search_query.py`)
ชั้นนี้ย้ายตามไปได้หมดไม่ว่าจะเปลี่ยนเอนจินข้างหลังเป็นอะไร

## 3. แผนต่อไป (ทำตามลำดับ ไม่ต้องกระโดด)

**ขั้นที่ 1 — เสร็จแล้ว** ตัดคำไทย · คำพ้อง · รหัสหลายรูปแบบ · เดาคำผิด · คะแนนความตรงแบบรวมชั้น
· โหมดตีความประโยค · กล่องแนะนำใต้ช่องค้นหา
ทั้งหมดอยู่บนฐานเดิม ไม่มี service เพิ่ม รองรับได้สบายที่ระดับ 25,000 SKU (วัดได้ 20–200ms/คิวรี บน SQLite)

**ขั้นที่ 2 — ย้ายขึ้น Postgres แล้วทำเมื่อคิวรีเริ่มเกิน 300ms**
เก็บผลตัดคำลงคอลัมน์ `search_text` + `tsvector` แล้วทำ GIN index · เติม `pg_trgm` ไว้ทนคำผิด
ชั้น `search_query.py` ใช้ต่อได้ทั้งหมด เปลี่ยนแค่ตอนประกอบ where

**ขั้นที่ 3 — Meilisearch เมื่อของเกิน ~200k SKU หรืออยากได้ instant search จริงๆ**
sync จาก `materials` เป็นรอบ · ให้เอนจินรับผิดชอบ typo/prefix/facet · เก็บ `search_query.py`
ไว้ทำคำพ้องกับการดึงสี-ขนาด-งบเหมือนเดิม

**ขั้นที่ 4 — semantic เป็นชั้นเสริม (ไม่ใช่ชั้นหลัก)**
ใช้เฉพาะตอนค้นแบบคำต่อคำแล้วได้ศูนย์ หรือใช้ทำ "สินค้าใกล้เคียง" ในหน้าสินค้า
**ห้ามเอามาแทนการค้นด้วยรหัส** — เซลล์พิมพ์ MATNR แล้วต้องได้ตัวนั้นเป๊ะทุกครั้ง

**ตลอดทาง — วัดผลจากของจริง**
ตาราง `search_queries` เก็บคำค้นกับจำนวนผลอยู่แล้ว ดู `GET /admin/top-searches`
คำที่ค้นบ่อยแล้วได้ศูนย์คือรายการงานที่ควรทำก่อนเสมอ (เติมคำพ้อง / แก้ชื่อสินค้า / เพิ่มคำในคลังคำ)

## 4. ข้อจำกัดที่ยังเหลืออยู่ (รู้ไว้ก่อนเจอ)

- **คำทับศัพท์** — พิมพ์ "อาดอร์น" หายังไงก็ไม่เจอ "Adorn" (ต้องมีตารางเทียบเสียง หรือรอ Meili/ES)
- **คลังคำสร้างจากข้อมูลในฐาน** แคชไว้ 10 นาที · ของเข้าใหม่แล้วล้างแคชให้เองตอน import
- **สีมาจากช่อง `color` ที่ต้นทางเขียนไม่เป็นมาตรฐาน** ("ขาว" / "สีขาว" / "สีขาว-แดง") จึงจับแบบ "มีคำนี้อยู่"
- **`LIKE '%...%'` ใช้ index ไม่ได้** — ที่ 25k แถวยังไม่เป็นปัญหา แต่นี่คือเพดานที่จะพาไปขั้นที่ 2
